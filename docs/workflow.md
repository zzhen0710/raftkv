# 项目驱动学习与开发流程

生效：2026-10-19。适用于 RaftKV 的后续任务。版本范围见 [ROADMAP](../ROADMAP.md)，代码标准见 [CODING](../CODING.md)，测试策略见 [testing](testing.md)。

## 工作单元与分工

- v0.1 等目标版本作为一章；小节使用 v0.1/S01、v0.1/S02。小节编号不冒充软件补丁版本，正式交付标签可使用 v0.1.0；创建标签和发布仍需明确授权。
- 一章采用“总览 → 逐节讲解与实践 → 章节总结”。不要求本人先读完课程、独立设计架构或先画图；AI 先提供设计、计划图和必要知识，再在当前任务中解释与纠正。
- 本人优先实现核心逻辑，阅读审查方案并决定采纳范围；AI 负责讲解、伪代码、设计图、审查、经批准的完善与验证。允许委托机械工作，不把手写行数当成能力证据。
- 每次只交付一个当前工作单元；批准整条路线不自动授权生成全部小节、完成整章源码或提交/推送。
- 新章节第一次请求只生成总览 note；后续每次生成一个小节 note。设计图由 AI 先提供并标明“计划设计/当前实现”，随实际实现更新。本人逐渐练习解释、预测和局部设计，不设置独立预习课程。

## 章节总览

位置按需采用 docs/learning/v0.1/README.md；章节目录只在实际生成总览时创建。

总览必须说明：问题与最终可观察行为、版本边界、先前能力、计划架构/请求路径图、模块职责、分节顺序及理由、每节交付与验收。不要先锁死远期接口或填满所有未来目录。

总览表列出小节编号、名称、目标和状态。尚无 note 的名称保持纯文本；note 实际生成后改为有效相对链接，完成状态独立表示：

未开始 → 待实现 → 待审查 → 待批准 → 待验收 → 已验收。

测试失败时退回相应待处理状态，不为推进日程标记完成。“已验收”表示约定范围经实现与验证，不等于本人对全部知识已熟练掌握。

## 小节 note

位置按需采用 docs/learning/v0.1/01-build-and-run.md 等主题文件名。正文以中文为主。每节至少覆盖：

1. 位置与目标：已有能力、本节增加的行为、范围与不做事项。
2. 原因与必要理论：为什么需要这些模块、主要取舍、当前恰好用到的知识；遇到陌生语法给短示例，并继续解释到能够尝试实现。
3. 实现地图：相对路径、文件职责、接口契约、调用与所有权关系、建议实现顺序。
4. 分模块详细伪代码：输入/输出、前后条件、数据与状态变化、判断/循环、必要检查、失败分支、资源生命周期和执行顺序。不能用“处理错误/完成复制”等空白步骤代替关键逻辑。
5. 练习分工：核心练习、可委托部分、暂不实现；核心测试断言也可作为本人练习。
6. 验证：测试文件/语言、初始状态、输入与预期、边界/失败用例、典型错误应该触发哪个测试、实际运行入口。解释测试意图，不照抄实现作为唯一预期。
7. 结果：完成后补充关键调整、理由、验证证据、限制及必要的理解检查。

伪代码应足够支持独立实现，具体 C++ 写法和局部组织留给本人尝试。完整实现留源码；聊天审查可提供完整替换文件，不把完整生产代码长期复制进 note。

## 自写、审查与批准落地

- 本人按 note 尝试实现。明确委托可标 TODO(ai)，疑问可标 TODO(question)；普通留空不自动等于授权填充。已明确委托且属于当前任务的机械内容无需反复确认。
- 请求“审视实现”时，先只读审查与必要验证，不先改源码；逐项核对当前变更、相关调用、接口和测试，说明审查范围与未执行的检查。
- 按当前项目约束下的健壮性、类型/资源安全、可维护性审查，不因本人写法基础而降低标准。该采用的现代 C++、安全转换、错误处理与结构改进应主动提出；每项改进给出收益与代价，不无依据地声称全局最优。
- 必须修复的问题与可选改进分开；必要检查遗漏明确指出位置、后果和验证方法。窄化转换先验证范围，不能只靠 cast 消除警告；并发、生命周期和持久化保证需要实际推理与证据。
- 常规异常处理和日志补充融入完整建议代码，不单独列为学习成果或调整记录。遗漏必要检查必须单列；影响接口、失败语义或一致性/持久性承诺的变化仍需说明契约与测试。
- 建议包含受影响文件的完整新增/替换代码，保留无关文件与正确实现。本人审视并批准后，才按采纳范围落地；受批准修改直接影响的必要回归一并执行。
- 验收包括相关测试、必要累计回归与一两个关键解释/预测问题。解释不清时补充当前问题的小实验，不要求重学整章或另开课程。

## 记录与文档分工

| 载体 | 保存内容 | 更新时机 |
| --- | --- | --- |
| Git commit | 一个逻辑完整变更的内容与理由 | 修改和对应验证完成后，由本人手动执行 |
| 小节 note 末尾 | 关键调整 → 原因与取舍 → 验证依据 | 小节验收时 |
| 章节总结 | 全流程、关键不变量、取舍、典型失败与剩余限制 | 本章全部验收后 |
| ADR | 有合理备选且影响后续实现的重要决策 | 确有此类决策时 |
| CHANGELOG | 面向使用者的重要版本变化 | 先收录实质变更，发布时汇总 |
| README | 实际状态、构建运行与文档入口 | 对应信息变化时 |
| 独立故障分析 | 跨多个小节的重要问题及复现/修复证据 | 确有必要时 |

不另设强制日报或日期流水账；主题和版本为主，日期、适用版本、已有提交是元数据。长期排查或性能实验按需保留时间线。细微排版、重复代码整理和常规补全不逐条登记。

完整项目证据留 RaftKV；经验证且可迁移的工程方法才进入 engineering-practices，AI 协作方法才进入 ai-coding-notes，各自链接项目依据，不要求每节更新三个仓库。私人中枢仅记决定、里程碑和入口。

## 小节收尾与版本交付

1. 检查 Diff、当前小节验收与相关累计回归，记录实际命令、结果及限制；文档任务不运行无关功能测试。
2. 更新总览有效链接和状态，小节末尾补关键调整；仅在状态/入口/使用方式变化时更新 README。
3. 给出明确文件列表及 add、暂存检查、commit、push 指令；本人手动执行。一个小节可对应多个有明确目的的提交，测试和必要文档随相关代码提交；纯格式批量变化另分提交。
4. 不默认暂存、提交、推送、创建 tag/release，不自动重写已共享历史。需要时只在当前明确授权范围内执行。
5. 本人报告已提交/推送后按需只读核对；不要为给 note 写入其自身提交哈希而制造追加提交。push 是同步，不自动代表发布或版本验收。
6. 一章结束生成总结 note，进行章节回归及小变式/关键解释验证；通过后才能将对应软件版本记为已交付。

## 目录与工程资料

源码按长期模块组织，不按学习小节复制工程。以下职责随实际内容建立，当前不创建空目录：

| 位置 | 职责 |
| --- | --- |
| src/kv、raft、storage、transport、server | 模块实现，初期头文件与实现就近组织 |
| apps | 可执行入口，不承载全部业务逻辑 |
| tests/unit | C++ 直接接口与内部状态验证 |
| tests/integration、tests/fault | Python 为主的程序/进程测试与故障编排 |
| tests/support | 确有复用需要的测试辅助实现 |
| docs/learning | 章节总览、小节与总结 |
| docs/decisions | 必要 ADR；不预先创建一套空决策 |
| docs/testing.md | 测试策略、实际入口和覆盖缺口 |
| scripts | 必要且有明确使用者的辅助入口 |
| .github/workflows | 与本地入口一致、分阶段接入的 CI |

构建依赖由 CMake 管理，Python 测试依赖单独声明，所需环境与命令随工程建立核实。CMakeLists、共享 preset、格式配置在 S01 引入；机器私有 preset、环境、构建产物、覆盖报告与普通运行数据不提交。许可证与第三方声明在确定发布/复用条件时核对，不擅自替本人选择授权条款。

源代码与测试保存完整实现，README 保存使用入口，重大决策/故障才另写专题，CHANGELOG 从真实软件变更开始维护。当前规范调整由本次 Git 提交说明，不制造“软件版本已发布”的记录。

## 首次开工顺序

先读 [项目导引](project-overview.md) 建立总体认识，再按 [ROADMAP](../ROADMAP.md) 进入 v0.1。开工第一轮生成章节总览，不直接实现业务代码。

v0.1 建议四节：S01 最小可构建工程与测试入口；S02 内存 KV 核心；S03 终端使用与 Python 程序测试；S04 累计覆盖审计与交付。具体分工在首次章节总览中确定，随后逐节实施，最后生成章节总结。测试从 S01 开始，S04 检查遗漏而非最后才补测试。

S01 的必要 C++20/Ninja/clang-format/CMake 配置可明确委托 AI；本人亲自构建、运行、调试并解释文件用途。所有工具与源码的完成状态以实际执行为准。
